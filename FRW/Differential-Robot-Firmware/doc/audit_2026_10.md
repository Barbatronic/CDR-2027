Audit complet de `src/` (~4 000 lignes) réalisé le 2026-10-30 sur le commit `19b0b45`.
Build OK, aucun warning (Flash 27 %, RAM 25 %).
Les numéros de ligne correspondent à ce commit : ils peuvent avoir bougé depuis.

**Synthèse :** code propre et bien structuré. Le principal risque en match est
l'absence de garantie d'arrêt à 100 s, et plusieurs chemins d'erreur qui
échouent silencieusement (calage, goto interrompu, relance sans reboot).

Cocher les cases au fur et à mesure des corrections.

## 🔴 Critique — peut coûter un match

### 1. Pas de coupure garantie à 100 s
- [ ] Corrigé

L'arrêt dépend de points de contrôle coopératifs dans la stratégie. Plusieurs
fonctions bloquantes ne vérifient pas `isMatchOver()` : `launchBalls()` (~5,5 s),
`moveBras()`, le recul obstacle `_motion->go()` dans la tâche motion.
Exemple : tir lancé à 96 s → ventilateur et roues du lanceur actifs jusqu'à ~101,5 s.

- Où : [main.cpp:218-222](../src/main.cpp#L218-L222)
- Correctif : tâche « chrono » haute priorité, indépendante de la stratégie, qui
  à `MATCH_DURATION_MS` coupe EN steppers, `stopFlywheels()`, `feeder.stop()`.

### 2. Tir déclenché depuis n'importe où après interruption endgame
- [ ] Corrigé

Si l'endgame (85 s) interrompt un `gotoXYenc`, celui-ci rend la main sans le
signaler ; `tirerDepuisCour()` enchaîne alors `launchBalls()` depuis la position
atteinte.

- Où : [strategy.cpp:214-220](../src/strategy/strategy.cpp#L214-L220)
- Correctif : `gotoXYenc` retourne un `bool` (arrivé / interrompu), testé avant le tir.

### 3. Relance d'un match sans reboot cassée
- [ ] Corrigé

`_nearEndMode` n'est jamais remis à `false`, `match_start_ms` jamais remis à 0.
Après un match d'essai puis retour WAIT_INIT par l'UI, `isMatchOver()` reste vrai :
- `goPID` / `turnPID` / `gotoXYenc` rendent la main immédiatement ;
- `goStall` s'arrête au premier poll ;
- → le calage échoue **silencieusement** avec une pose fausse.

Avec RESTART_MATCH, l'endgame n'interrompt plus rien.

- Où : label `restart:` [main.cpp:126](../src/main.cpp#L126), [robot.h:90](../src/strategy/robot.h#L90)
- Correctif : remettre `match_start_ms = 0` et `_nearEndMode = false` (ajouter un
  `Robot::resetMatch()`) au label `restart:`.

### 4. Commandes d'arrêt UI ignorées pendant la stratégie
- [ ] Corrigé

`gStateCmd` n'est lue qu'avant le match et après le retour de `runStrategy*()`.
Pendant toute la stratégie, `stop_motors` / `stop_match` n'ont aucun effet.

- Où : [main.cpp:195-210](../src/main.cpp#L195-L210)
- Correctif : traiter STOP_MOTORS directement à la réception (release + disable),
  ou lire la file dans `Robot::waitArrived`.

### 5. Tirette sans anti-rebond
- [ ] Corrigé

Un rebond à l'insertion (LOW puis HIGH < 20 ms) suffit à démarrer le match.

- Où : [main.cpp:178-183](../src/main.cpp#L178-L183), [buttons.cpp:11](../src/io/buttons.cpp#L11)
- Correctif : exiger un état stable 100–200 ms (insertion et retrait).

### 6. Configuration committée ≠ configuration de match
- [ ] Corrigé

- `TIR_ATTENDRE_PHASE_ATTAQUE 0` alors que le commentaire le dit « obligatoire en match » ;
- `WIFI_USE_STA 1` ;
- WebSocket sans authentification : n'importe qui sur le WiFi du makerspace peut
  lancer un match, un goto ou les roues du lanceur.

- Où : [config.h](../src/config.h)
- Correctif : un `[env:match]` dans `platformio.ini` avec des `-D` dédiés, et des
  gardes `#ifndef` dans `config.h`.

## 🟠 Important

### 7. Obstacle persistant = robot bloqué jusqu'à l'endgame
- [ ] Corrigé

Après `OBS_WAIT_MS`, le robot repart, redétecte, recule 100 mm à l'aveugle (sans
vérifier l'arrière), et recommence indéfiniment. `waitArrived` n'a pas de timeout :
la stratégie ne peut jamais choisir un autre objectif.

- Où : [motion_ctrl.cpp:163-185](../src/motion/motion_ctrl.cpp#L163-L185)
- Correctif : abandon après N tentatives, statut « bloqué » remonté à la stratégie.

### 8. Trajet de retour vers la cour proche de la tour jaune 2
- [ ] Vérifié sur table

Calcul géométrique sur les POI, non testé sur table. Après la dépose sur
`murYellow_2`, le robot est vers (877, 373). Le trajet vers `entree` (1150, 1000)
passe à **75 mm du bord** de `tourYellow_2` (850, 750, Ø200) : dans le rectangle
de détection (±100 mm) → la tour peut être prise pour un adversaire (→ point 7),
voire contact physique selon la largeur du robot.

- Où : [strategy.cpp:207-215](../src/strategy/strategy.cpp#L207-L215)
- Piste : point de passage intermédiaire, ou mode `WALL_FILTERED` étendu aux éléments fixes.

### 9. Calage : échecs silencieux possibles
- [ ] Corrigé

- La valeur de retour de `goStall` est ignorée : si le robot ne touche pas la
  bordure en 250 mm, `setPosition` suppose quand même le contact.
- À 10 % d'accélération (150 mm/s²), le déplacement par poll reste sous le seuil
  de blocage (0,5 mm) pendant ~170 ms au démarrage ; la confirmation prend 150 ms.
  Marge d'environ un poll contre un faux blocage. A fonctionné en 2026 avec le
  même réglage, mais la marge est quasi nulle.

- Où : [strategy.cpp:62-111](../src/strategy/strategy.cpp#L62-L111), [robot.cpp:97-170](../src/strategy/robot.cpp#L97-L170)
- Correctif : armer la détection de blocage après la rampe d'accélération (ou
  après quelques mm), tester le retour de `goStall` et signaler l'échec (LED/log).

### 10. Rotations : mélange des deux empattements
- [ ] Corrigé

Erreurs calculées sur les roues codeuses (189 mm), envoyées telles quelles aux
roues motrices (145,6 mm) : gain ×1,3 en rotation, et courbe de freinage qui
demande 1,3 × l'accélération autorisée aux steppers → dépassement probable.
Le contrôleur pose-based (`_runPoseStep`) utilise aussi `encWheelbase` pour
répartir ω sur les roues motrices.

- Où : [motion_ctrl.cpp:409-461](../src/motion/motion_ctrl.cpp#L409-L461), [motion_ctrl.cpp:535](../src/motion/motion_ctrl.cpp#L535)
- Correctif : multiplier la partie différentielle par `wheelbase / encWheelbase`.

### 11. Reprise après obstacle pendant un blend : mauvaise direction
- [ ] Corrigé

Après le recul, la reprise appelle `_initTranslatePhase()` (wheel-PID tout droit
selon le cap actuel). Pendant un blend, ce cap ne pointe pas vers la cible.
Seuls les clics UI déclenchent un blend aujourd'hui.

- Où : [motion_ctrl.cpp:171](../src/motion/motion_ctrl.cpp#L171)
- Correctif : appeler `_initAlignPhase()` à la place.

## 🟡 Mineur

- [ ] **Calibration live non validée** : `encWheelDiam=0` depuis l'UI → division
  par zéro puis cast `inf → int32` (comportement indéfini).
  [log_server.cpp:433](../src/wifi/log_server.cpp#L433) — valider `val > 0`.
- [ ] **Filtre PCNT** à 12,5 µs ; demi-cycle du signal A ≈ 15 µs pour une roue
  codeuse à 2 600 mm/s (rotation à 2 000 mm/s) → pertes de pas possibles.
  Passer à ~400 (5 µs). [encoder.cpp:37](../src/motion/encoder.cpp#L37)
- [ ] **Deux sources de pose** : `Robot::getX()` et la détection obstacle de
  `Robot` utilisent la pose steppers, `MotionController` la pose encodeurs. Le
  calage fait `setPosition(robot.getX(), …)`. Unifier sur la pose encodeurs.
- [ ] **Code dupliqué / mort** :
  - détection obstacle en double dans `Robot` et `MotionController` ;
  - `runCalibration()` jamais appelée, son commentaire parle d'un `go(1000)` absent ;
  - état `HOLD` jamais utilisé ;
  - paramètres de `_initBlendPhase` ignorés.
- [ ] **Petits défauts** :
  - LEDs : `LIDAR_OFFSET_DEG` au lieu de `gCalib.lidarOffsetDeg` ([leds.cpp:62](../src/io/leds.cpp#L62)) ;
  - commentaire « ~3600 RPM » du LIDAR : c'est ~3600 °/s, soit ~600 tr/min ;
  - commentaire de `DEFAULT_ACCEL_MMS2` périmé ;
  - JSON LIDAR copié pendant que la tâche WiFi l'envoie → trame corrompue occasionnelle.
- [ ] **Piles des tâches** : motion et stratégie à 4 Ko avec `printf` de floats.
  Logger `uxTaskGetStackHighWaterMark` une fois pour vérifier la marge.
